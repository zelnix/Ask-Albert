# RCA — quant-features (Ask Albert) — run a9a1826c-c89d-446b-b8f3-19faa8c6a185

## Symptoms reported
- "Ask Albert" chat always replies: *"I cannot reach the evidence service right now. Please try again later."*
- Dashboard cards show **Stale** (Albert's Brief, BTC Bull & Bear, Paper Trading, Portfolio & Risk).

## Verdict: TWO independent root causes (both runtime; live app, active run succeeded)

### Root cause #1 — "Ask Albert" fallback = upstream HTTP 429 on the evidence/news fetch (CODE / EXTERNAL)
Backend traceback (live pod logs, active run):
```
File "/app/backend/server.py", line 1022, in fetch_news
    with urllib.request.urlopen(req, timeout=timeout) as r:
urllib.error.HTTPError: HTTP Error 429: Too Many Requests        (x17+ in window)
...
    obj = json.loads(raw[s:e + 1])
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)   (x25+)
```
- The chat's "evidence service" is `fetch_news()` (server.py:1022), which calls an **external provider over `urllib`** and is being **rate-limited (HTTP 429)**. On 429 the body is empty/non-JSON, so `json.loads(raw[s:e+1])` raises `JSONDecodeError`; the handler then returns the generic "cannot reach the evidence service" message for every query. This is persistent and independent of the restarts below.
- **Gemini is NOT the cause.** `GEMINI_API_KEY` is present and non-empty in production secrets (also `EMERGENT_LLM_KEY`, `GEMINI_MODEL`, `CHAT_MODEL_*` all set). The failure happens at the evidence-gathering step, before/around the external news fetch — not at the Gemini call.
- NOT reproduced in an eph sandbox: the fault is an external API's live rate-limit/quota, which the sandbox (no secrets, no external creds) cannot exercise. Diagnosed from the production traceback only.

### Root cause #2 — Pod OOMKilled at the tier_0 memory ceiling → backend unavailability + scheduler resets (TIER / RESOURCE)
Pod events (active run):
```
last_termination: OOMKilled (exit 137) at 2026-10-01T13:50:47Z, restarts=3
Liveness/Readiness/Startup probe failures on :3000 (connection refused / EOF)
Killing: failed liveness probe, will be restarted
```
`get_tier`: tier_0 "Starter", memory 200Mi / **limit 512Mi**, cpu 50m/250m, replicas 2.
- This is a `nextjs_mongo_shadcn_base_image` app: a **single container runs BOTH** the Next.js server (:3000) and the FastAPI backend (:8001). When the container is OOMKilled, both go down together. During each restart window the Next.js api-proxy logs:
```
[api-proxy] GET/POST http://localhost:8001/api/v1/... -> backend_unavailable: nothing is listening on http://localhost:8001 (ECONNREFUSED)
```
  (seen for /dashboard, /ticker, /alerts, /albert/brief, /albert/ask, etc.)
- The **APScheduler engine lives inside the FastAPI process**. Each OOM kill (restarts=3) tears it down and restarts it mid-cycle, interrupting the data-refresh jobs → cards go **Stale**. I did not find an explicit "scheduler started" log line in the window, so continuous scheduler operation could not be positively confirmed — but the repeated OOM restarts would interrupt it regardless. The same upstream 429s (root cause #1) also break the refresh jobs even when the backend is up, compounding staleness.

## Why the two symptoms map cleanly
- "Ask Albert always fails" → root cause #1 (evidence/news 429), returns 200 HTTP with the fallback text.
- "Stale" cards → root cause #2 (OOM restarts interrupting the scheduler + backend) AND root cause #1 (refresh jobs hit the same 429).

## Recommended fixes
1. **CODE (E1)** — Harden `fetch_news()` in `backend/server.py` (~line 1022):
   - Handle HTTP 429 explicitly: exponential backoff + retry, and **serve last-cached evidence** instead of hard-failing the whole chat answer.
   - Guard the `json.loads(raw[s:e+1])` parse against empty/non-JSON bodies (try/except → graceful degradation) so a provider hiccup doesn't blank the dashboard/chat.
   - Reduce call volume (cache/share results across the scheduler jobs and the /ask path) so the provider stops rate-limiting.
2. **USER** — Check the external news/evidence provider that `fetch_news()` calls: confirm the API key/plan is valid and the **rate-limit/quota isn't exhausted** (the 429 is upstream). Raise the plan or add a key with higher limits if needed.
3. **USER** — **Upgrade the deployment tier** (Deployment Panel → Resources). The pod is OOMKilled (exit 137, reason=OOMKilled, restarts=3) at the tier_0 512Mi limit; moving off that ceiling stops the restart churn that makes the backend unavailable and resets the scheduler. If profiling later shows a specific memory hotspot, add a targeted CODE fix too.
